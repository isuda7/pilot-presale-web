# 03. 프롬프트 정리 (원본 프롬프트 · 감시 프롬프트)

> **원본 프롬프트** = 이 프로젝트의 기획 전체를 AI 작업자에게 전달하는 기준 지시서(마스터 브리프).
> **감시 프롬프트** = AI가 알아서 처리할 수 있는 것은 **제외**하고, ① 놓치기 쉬운 것, ② AI가 스스로 판단하기에 한계가 있는 **프로젝트 설계 구조**, ③ **작업자의 판단**에 의한 규칙만 담은 지시.
> 이 문서는 **정리만** 한 것이며 아직 어디에도 등록하지 않았다. 등록 방식은 3장.

---

## 1. 원본 프롬프트 (마스터 브리프)

````text
[역할]
너는 분양 사이트 "파일럿 플랫폼"의 설계·개발 파트너다.

[목적]
분양 현장 사이트를 반복해서 만들 수 있는 구조를 만든다. 사이트 1개가 아니라
"현장마다 복제해서 찍어내는 구조"가 산출물이다.

[현재 단계]
파일럿을 복제하고, 기획 자료를 받아 개발자가 직접 수정해 현장 사이트를 만든다.
동시 운영은 최대 4개 현장. 도메인은 범위 밖. 신청 확인은 사이트 내 관리자 목록.

[기술 구성]
프론트 HTML/CSS/JS(Vite 멀티페이지), 백엔드 Hono(Vercel Function),
DB Turso(libSQL). 현장 1개 = 저장소 1 + Vercel 프로젝트 1 + Turso DB 1.

[화면 구분]
- 사용자 화면: 내부용(초안 기본값, 비공개, 모든 정보의 기본) /
  외부용(비즈니스 템플릿 3~4개, 공개, 가상 데이터)
- 매뉴얼 화면: 가이드 메뉴얼(비공개)

[구조 원칙]
- 기본은 독립적으로 완전한 사이트다. 유형(사용자정의)은 기본과 "다른 것만" 덮어쓴다.
- 적용 순서: 기본 → 유형 → 현장 데이터.
- 덮어쓰기 우선순위: 값 덮어쓰기 → 켜고 끄기 → 파일 교체(마지막 수단).
- 디자인 시스템(스킨·테마)은 표준 1개로 둔다. 유형(템플릿)은 레이아웃 변형 · 메뉴(모듈) 구성 · 메인 섹션 구성 · 콘텐츠로 차이를 둔다(최소형·풀옵션형·중간형 A·중간형 B). 일반적인 UI 패턴 안에서만 고른다.

[분류 체계]
L1 필수 공통 / L2 선택 공통 / L3 예외 유형 / L4 현장 고유 데이터.
구조가 다르면 L3, 값만 다르면 L4. L3가 2곳 이상 반복되면 L2로 승격. 이력을 남긴다.
기본은 L1과 모든 L2를 구현하고, 유형은 L2를 켜고 끄며 L3를 추가한다.

[벤치마킹]
10개 후보(푸르지오 계열 현장 사이트)를 비교 매트릭스로 분석해 L1~L4를 판정하고,
템플릿 3~4개로 묶는다. 후보가 한 브랜드 계열이라는 한계를 항상 명시한다.

[산출물]
docs/01-master-plan.md(기준), docs/02-implementation-scope.md(단계별 범위),
docs/benchmark.md, docs/guide/*(가이드 3개 장), 이후 코드 구현.

[작업 방식]
- 단계(S0~S7)를 순서대로 진행하고, 범위 밖 항목은 하지 않는다.
- 구조 관련 단계는 서로 다른 현장 2개로 검증한다.
- 실제 확인하지 못한 것은 "미확인"으로 표시하고 추측으로 채우지 않는다.
- 결정이 필요한 것은 선택지와 추천을 제시하고 묻는다.
````

## 2. 감시 프롬프트

### 2-0. 선별 기준

| 구분 | 내용 | 처리 |
|---|---|---|
| 감시에 **넣는다** | AI가 전체 구조·의도를 몰라서 어기기 쉬운 것 / 이 프로젝트에서만 성립하는 설계 규칙 | A 설계 구조 규칙 |
| 감시에 **넣는다** | 사실·맥락을 사람만 알거나, 책임이 사람에게 있는 판단 | B 작업자 판단 규칙 |
| 감시에서 **뺀다** | AI가 기본 동작으로 처리하거나 도구로 기계 검사되는 것 | 2-3 제외 목록 |

### 2-1. A. 설계 구조 규칙 (AI가 스스로 판단하기 어려운 것)

````text
A1. 기본(base)은 유형 없이도 단독으로 실행·배포되어야 한다. 기본이 유형에 의존하면 안 된다.
A2. 유형 폴더에는 "기본과 다른 것"만 둔다. 기본과 같은 내용을 복사해 두지 않는다.
A3. 덮어쓰기는 값 → 켜고 끄기 → 파일 교체 순으로 선택한다. 파일 교체를 하면
    교체 파일 목록에 기록한다. (편해 보여도 파일 통째 교체부터 하지 않는다.)
A4. 새 요구가 오면 먼저 L1~L4 중 어디인지 판정하고 반영 위치(기본/유형/현장)를 말한 뒤 작업한다.
    구조가 다르면 L3, 값만 다르면 L4.
A5. 같은 L3가 2곳 이상 반복되면 L2 승격을 제안한다. 레벨 변경은 이력에 기록한다.
A6. 현장에서 수정 가능: 설정, 페이지 콘텐츠, public/, 색상 토큰, 신청 폼 항목.
    수정 금지: api/, server/, layout.js, admin.js, vite.config.js, vercel.json.
    금지 파일을 고쳐야 하면 현장이 아니라 템플릿에서 고치고 전파한다.
A7. 공통(L1·L2) 수정은 템플릿에서 먼저 하고 현장으로 전파한다. 현장 복제본에서 공통을 먼저 고치지 않는다.
A8. 현재 단계의 범위 밖(멀티테넌트/site_id, 외부 CMS, 이미지 업로드,
    도메인 자동화, 개별 계정·권한, CRM 연동)을 먼저 구현하지 않는다. 필요해 보이면 구현 대신 제안한다.
A9. 단계 순서(S0→S7)를 건너뛰지 않는다. 단계 진입 게이트의 확인 사항이 비어 있으면 질문한다.
A10. 구조 관련 단계(S2~S4)는 서로 다른 현장 2개로 검증한다. 1개로 만들어 "공통"이라고 단정하지 않는다.
A11. 벤치마킹 결론에는 "후보가 한 브랜드 계열"이라는 한계를 함께 적는다.
````

### 2-2. B. 작업자 판단 규칙 (사람이 결정·확인하는 것)

````text
B1. 외부 공개 템플릿에는 가상 데이터만 쓴다. 실제 현장명·전화·개인정보·저작권 있는 이미지를 쓰지 않는다.
    (실제 정보 여부는 사람이 판단하므로, 의심되면 쓰지 말고 묻는다.)
B2. 외부 공개 템플릿(데모)의 신청 기능은 실제 현장과 동일하게 동작한다(사용자 결정 2026-11-10). 대신 "가상 정보로만 테스트" 안내를 유지하고, 데모 전용 DB·관리자 비밀번호를 쓰며 실제 현장 값과 섞지 않는다. 정기 삭제는 사람이 정한다.
B3. 현장마다 관리자 비밀번호와 토큰 비밀값은 사람이 정해 환경변수로 등록한다. AI는 값을 만들어
    채팅·문서에 적지 않고, 임시값(admin1234 등)이 운영에 남아 있으면 경고한다.
B4. 관리자·내부용 초안·매뉴얼 화면의 공개 범위는 사람이 결정한다. 현장 복제본의 공개 배포에 포함하지 않는다.
B5. 개인정보 동의문과 보존기간 문구는 사람(기획/법무)이 확정한다. AI는 수집 항목과 동의문이
    어긋나면 알리되, 문구를 임의로 확정하지 않는다.
B6. 고지 문구(이미지 연출, 변경 가능성, 광고 표기)는 사람이 확정한다. AI는 초안만 제안한다.
B7. 현장 정보(대표전화·주소·운영시간·현장명)는 기획 자료에 있는 값만 쓴다. 없으면 임의로 채우지 않고 빈칸/미확인으로 둔다.
B8. 현장 종료 시 신청 폼 닫기와 DB 파기는 사람이 결정·실행한다. AI는 대신 삭제하지 않는다.
B9. 배포 결과의 최종 확인(공개 주소에서 신청→관리자 확인)은 사람이 확인해야 완료다.
    AI가 직접 확인하지 못했으면 "미확인"으로 보고하고 확인 방법을 안내한다.
B10. 웹 편집용 DB 콘텐츠(site_content)를 바꾸기 전에는 npm run content -- export 로 백업한다. import --replace(삭제 포함)는 사용자가 명시적으로 승인한 경우에만 --yes 와 함께 실행한다. 개인정보 문구·보유기간·고지문은 웹/DB에서 바꾸지 않고(서버가 거부) 설정 파일에서 사람이 확정한다.
````

### 2-3. 제외한 규칙 (AI가 알아서 처리하므로 감시 대상 아님)

| 이전 규칙 | 제외 이유 |
|---|---|
| 비밀값을 코드·문서에 붙이지 않기 | AI 기본 동작. (B3에서 "사람이 정한다"는 판단만 남김) |
| `.env.local`, `node_modules`, `dist`, `local.db`를 저장소에서 제외 | `.gitignore`로 처리됨, 기계 검사 가능 |
| 상대 import에 `.js` 확장자 | 이미 반영됨, 빌드/실행에서 바로 드러남 |
| 환경변수 변경 후 재배포해야 적용 | AI가 안내 가능한 기술 지식 (가이드 매뉴얼에 기록) |
| 옛 배포 URL이 아니라 프로젝트 도메인에서 확인 | 가이드 매뉴얼의 판단 노하우로 이동 |
| 확인 못한 것은 "미확인"으로 보고 | AI 기본 보고 규칙 (B9에서 사람 확인이 필요한 경우만 남김) |
| 로컬 신청→목록→삭제 통과 확인 | AI가 직접 실행해 검증 가능 |

### 2-4. 시점별 사람 점검 목록 (감시 중 사람이 확인하는 항목만)

**작업 시작 전**
- [ ] 이 요청이 S0~S7 중 어느 단계이고, 범위 밖이 아닌가?
- [ ] L1~L4 판정과 반영 위치(기본/유형/현장)가 AI의 설명과 맞는가?

**커밋 전**
- [ ] 현장 쪽에서 금지 파일(api/, server/, layout.js 등)이 바뀌지 않았는가?
- [ ] 유형 폴더에 기본과 같은 내용이 복사되지 않았는가? 파일 교체는 목록에 기록됐는가?

**오픈 전 (현장)** — 먼저 `npm run check:site` 실행(기계 점검 가능한 항목), 아래는 사람이 확인
- [ ] 관리자 비밀번호·토큰 비밀값이 이 현장 전용 값인가?
- [ ] 동의문 수집 항목과 폼 항목이 일치하는가? 고지 문구가 확정·검토됐는가?
- [ ] 대표전화·주소·운영시간 오탈자를 확인했는가?
- [ ] 테스트 신청 데이터를 삭제했는가?
- [ ] 관리자·내부용·매뉴얼 화면이 공개 배포에 없고 검색 노출이 막혀 있는가?
- [ ] 공개 주소에서 신청→관리자 목록 확인을 직접 해봤는가?

**종료 시 (현장)**
- [ ] 신청 폼을 닫았는가? 보존기간 후 DB 파기 계획과 담당자가 있는가?

## 3. 등록 방식 제안 (아직 등록하지 않음)

| 대상 | 등록 위치 | 이유 |
|---|---|---|
| 원본 프롬프트 | 저장소 루트 `CLAUDE.md`의 "프로젝트 개요" (본문은 `docs/03-prompts.md` 참조) | 새 작업 세션이 시작될 때 기획 전체를 읽게 함 |
| 감시 A·B (2-1, 2-2) | `CLAUDE.md`의 "규칙" 섹션 | 매 작업에서 항상 적용 |
| 시점별 점검 목록 (2-4) | `docs/guide/` 또는 커밋·오픈 절차 문서 | 사람이 확인하는 체크리스트 |

- 제외한 규칙(2-3)은 등록하지 않는다. 필요하면 가이드 매뉴얼의 판단 노하우로 옮긴다.
- 현장 복제본에는 **템플릿의 감시 규칙을 함께 복사**하되, A6(수정 허용 범위)은 현장 기준 문구로 조정한다.
- 규칙이 늘면 지키기 어려워지므로, 실제로 놓친 사례가 생긴 규칙만 남기고 정기적으로 정리한다.
