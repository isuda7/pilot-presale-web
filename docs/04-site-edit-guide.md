# 04. 현장 수정 범위와 설정 구조 (S2 결과)

## 폴더 역할
| 위치 | 역할 | 현장에서 수정 |
|---|---|---|
| `config/site.ts` | L4 현장 데이터. 기본·유형과 **다른 값만** 적는 덮어쓰기(`SITE_OVERRIDE`) | ✅ |
| `config/base.ts` | 기본(base)의 완전한 설정값 | 템플릿에서만 |
| `types/<유형>/` | 유형 정의(`type.ts`), 디자인 토큰(`tokens.css`), 교체·추가 페이지(`pages/`) | 템플릿에서만 (현장은 사용할 유형 1개만 남김) |
| `config/modules.js` | L1/L2 페이지 목록(기본이 구현한 전부) | 템플릿에서만 (페이지 추가·레벨 변경) |
| `config/form.ts` | 신청 폼 항목 정의. 화면과 서버 검증이 함께 읽음 | ✅ (항목 이름은 name/phone/message 고정) |
| `src/css/tokens.css` | 디자인 토큰(색·폰트·폭) | ✅ |
| `pages/*.html` | 페이지 콘텐츠 | ✅ (`<main data-module>` 안쪽) |
| `public/` | 정적 파일 (`robots.txt` 포함) | ✅ |
| `src/css/common.css`, `src/js/*` | 레이아웃·동작 코드 | ❌ 템플릿에서 수정 후 전파 |
| `api/`, `server/`, `vite.config.js`, `vercel.json` | 백엔드·빌드·배포 | ❌ |

## 자주 하는 작업
- **현장명·전화·푸터 고지 변경**: `config/site.ts`에 해당 키만 적는다(키 구조는 `config/base.ts` 참고).
- **L2 페이지 끄기**: `config/site.ts`에 `modules: { community: false }` — 메뉴에서 빠지고, 직접 주소로 들어오면 메인으로 이동한다. 그룹 안 항목이 모두 꺼지면 그 메뉴도 사라진다. L1은 끌 수 없다.
- **색상 변경**: `src/css/tokens.css`
- **페이지 추가**: `config/modules.js`에 항목 추가(템플릿에서) → `npm run gen:pages`
- **방문예약형 현장**: `config/form.ts`의 `title`을 '방문예약'으로 바꾸면 메뉴와 제목이 따라간다.
- **신청 폼 항목 라벨·필수 여부 변경**: `config/form.ts`. 개인정보 동의문의 수집 항목은 여기서 자동 생성된다.

## 유형 선택과 덮어쓰기 (S3)
- 적용 순서: **기본(`config/base.ts`) → 유형(`types/<이름>/type.ts`) → 현장(`config/site.ts`)**. 객체는 항목 단위로 병합, 배열은 통째로 교체.
- 유형 선택: 환경변수 `SITE_TYPE` (없으면 기본). 없는 이름이면 빌드가 실패한다.
  - 개발: `SITE_TYPE=minimal npm run dev` / 빌드: `SITE_TYPE=minimal npm run build`
  - Vercel: 프로젝트 환경변수 `SITE_TYPE` 등록 후 재배포 (서버의 신청 폼 검증도 이 값을 따른다)
- 유형 정의(`type.ts`): `site`(값), `modules`(켜고 끄기), `addModules`(L3 모듈 추가), `form`(신청 폼 덮어쓰기).
- 디자인: `types/<이름>/tokens.css`에 기본과 다른 토큰만 둔다.
- 파일 교체: `types/<이름>/pages/<파일>.html` — 기본에 같은 이름이 있으면 교체(`index.html` 포함), 없으면 새 페이지 추가. **교체하면 `npm run type:report`로 `types/<이름>/REPLACED.md`를 갱신**한다(감시 A3).
- 새 유형 만들기: `types/<이름>/type.ts` 작성 → `types/index.ts`에 등록.

## 비즈니스 템플릿 4종 (S4)
**디자인 시스템(스킨·테마)은 1개**다(표준·무난·안정감). 템플릿 차이는 색이 아니라 **① 레이아웃 패턴 ② 메뉴(모듈) 구성 ③ 메인 섹션 구성 ④ 콘텐츠 양**으로 만든다. 기본(유형 없음)도 같은 디자인 시스템을 쓴다(내부용 초안).

| `SITE_TYPE` | 성격 | 메뉴 구성 | 헤더 · 히어로 · 서브 | 메인 섹션 구성 |
|---|---|---|---|---|
| `minimal` | **최소형** | L1만 (사업개요·입지·프리미엄·오시는길·언론보도·신청) | 간단한 헤더(드롭다운 없음) · 낮은 배너 · 서브 없음 | 사업개요 → 입지 → 프리미엄 → 오시는길 → 상담 CTA |
| `full` | **풀옵션형** | L1 + L2 전부 + L3(오피스텔·근린생활시설) | 로고+메뉴+전화 헤더 · 전체 사진 히어로+요약 카드 · 서브 **탭** | 바로가기 → 사업개요 → 분양일정(타임라인) → 입지 → 프리미엄 → 평면 → 커뮤니티 → 영상 → 보도 → CTA |
| `mid-a` | **중간형 A · 분양정보형** | L1 + 분양일정·공급·모집공고·계약안내·단지설계·배치도·평면 | 일반 헤더 · 좌 글/우 사진 히어로 · 서브 **좌측 메뉴** · 방문예약 | 분양일정 → 사업개요 → 공급 → 평면 → 입지 → CTA |
| `mid-b` | **중간형 B · 상품·입지 비주얼형** | L1 + 단지설계·커뮤니티·배치도·평면·E-모델하우스·인테리어·영상·이벤트 | 로고 중앙 헤더 · 가운데 정렬 사진 히어로 · 서브 없음(경로 표시) · 제목 가운데 정렬 | 프리미엄 → 입지 → 커뮤니티 → 평면 → 영상 → CTA |

- **레이아웃 변형**(`SITE.layout`, 유형 또는 현장이 선택): `header`(`bar`·`center`·`simple`), `hero`(`full`·`center`·`split`·`banner`), `sub`(`none`·`tabs`·`side`), `sechead`(`left`·`center`), `heroPos`/`imgPos`(사진 초점). 구현은 `common.css`의 `html[data-header|data-hero|data-sub|data-sechead]`와 `layout.js`. **일반적으로 쓰는 패턴 안에서만** 고른다(튀는 UI를 넣지 않는다).
- **메인 섹션 구성**(`SITE.home`): 섹션 키 배열. 모듈 키(`biz`, `schedule`, `location`, `premium`, `unit`, `community`, `video`, `press`…) 또는 `quick`(바로가기)·`cta`(상담 배너). 꺼진 L2 모듈은 자동으로 빠진다. 렌더링은 `src/js/home.js`(`schedule`은 타임라인, `biz`·`directions`는 이미지+표, 나머지는 이미지·표·카드·목록).
- **메뉴(모듈) 구성**: 유형의 `modules`로 L2를 켜고 끈다. `full`만 `addModules`(L3)와 `pages/`(추가 페이지)를 사용한다.
- **콘텐츠**: 유형마다 가상 프로젝트가 다르고 `types/shared/virtual.ts`의 프로필(`MINIMAL`·`CLASSIC`·`URBAN`·`NATURE`)에서 항목 수·문구가 다르다. 전화 `000-0000-0000`, 날짜·수치는 가상.
- **이미지**: 유형마다 이미지 세트가 따로 있다. 해석 순서: ① 사진 `src/assets/photos/<유형>/<모티프>.jpg|webp|png` → ② 유형별 CG `src/assets/art/<유형>/<모티프>.svg` → ③ 기본 CG `src/assets/art/default/`. 같은 이름의 사진을 넣으면 코드 수정 없이 우선한다. 모티프 8종: hero·building·location·park·plan·interior·community·video.
  - 현재 사진은 유형마다 hero·building·interior·community·park 5장씩 **Pexels 무료 사진 20장**(Pexels License, 상업적 이용 가능·출처 표기 불필요, 사용자 승인 후 다운로드). 출처는 `src/assets/photos/CREDITS.md`. 처음 받은 사진 중 보기 좋지 않은 9장은 검토 후 교체했다.
  - 사진 선정 기준: 표시 프레임(21:8, 히어로 16:9)으로 잘라도 구도가 살아 있고, 선명하며, 유형끼리 겹치지 않을 것. 새 사진도 실제 프레임으로 잘라 본 뒤 결정한다.
  - `location`(지도)·`plan`(평면도)은 사진이 아니라 CG 도면을 쓴다. `video`는 hero 사진에 재생 버튼을 얹는다. CG는 `node scripts/gen-art.mjs`로 생성한다(팔레트는 스크립트의 `SKINS`).
  - **데모용이다.** 실제 현장은 현장 사진으로 교체하고 데모 사진·`CREDITS.md`는 삭제한다. 사진에 실제 건물·인물이 있을 수 있어 그대로 쓰지 않는다.
- **참고한 후보 사이트**: 후보(`docs/benchmark.md`)의 일반적인 구성 패턴(상단 메뉴, 사업/분양/계약/단지/세대/홍보 구성, 풀블리드 히어로, 좌측 메뉴, 탭, 중앙 로고 헤더)을 참고하되 **이미지·문구·로고·코드는 가져오지 않는다**(저작권, 감시 B1). 디자인은 특정 사이트를 따라 하지 않고 무난한 표준 하나로 통일했다.
- **디자인 변경 이력(사용자 요청, 2026-11-10)**: 스킨(색·테마)별 템플릿은 폐기했다. 이미지는 유지했고 유형 이름으로 정리했다.
- **현장 복제 시**: 쓰지 않는 유형 폴더, `src/assets/photos/<다른 유형>`, `src/assets/art/<다른 유형>`, `src/assets/photos/CREDITS.md`, 샘플 프로필 데이터를 지운다(가이드 1장 6절).

## 인라인 편집 (사용자 화면에서 바로 수정)
관리자 편집 화면과 별개로, **사이트 화면 그 자체에서** 문구·행·이미지를 고치고 저장한다(2026-11-10, 사용자 요청). 기본 사이트와 템플릿 4종 모두 같은 방식이다.

- **들어가는 법**: ① 관리자 화면(`/pages/admin.html`) 로그인 → **사이트에서 직접 편집 ↗** 버튼, 또는 ② 로그인한 브라우저에서 사이트 주소 끝에 `?edit=1`. 로그인하지 않으면 `?edit=1`은 관리자 로그인으로 보낸다. **방문자에게는 편집 코드가 아예 로드되지 않는다**(관리자 토큰이 있을 때만 불러옴).
- **편집 바**(화면 하단): 편집 모드 켜기/끄기, 수정한 항목 수, **저장**, **변경 취소**, 관리자 화면 링크. 저장하지 않은 채 나가면 경고한다.
- **편집 모드에서 하는 일**
  - 점선으로 표시된 문구를 눌러 바로 고친다: 현장명·전화·주소·운영시간, 메인 제목·설명·소제목·보조 버튼, 요약 수치, 소개 문단, 표 셀, 카드 제목·설명, 목록 항목. 같은 값이 여러 곳(헤더·푸터·상담 배너)에 있으면 함께 바뀐다.
  - **행·카드·항목 추가(＋)와 삭제(✕)**: 표 행, 카드, 목록, 요약 수치, 분양일정 타임라인. 한도는 표·목록 30, 카드 12, 요약 수치 6.
  - **이미지 변경**: 이미지 위 버튼 → 목록에서 선택(그 유형의 사진/이미지 세트).
  - 링크는 편집 중에 이동하지 않는다. Enter 줄바꿈과 서식은 지원하지 않고, 붙여넣기는 일반 텍스트로 들어간다.
- **저장**: 변경된 저장 단위만 관리자 편집 화면과 **같은 API·검증·이력**으로 보낸다. 기본 정보는 바꾼 필드만 DB에 쓴다(안 건드린 필드는 파일 기본값 유지). 본문 항목은 그 항목 전체(이미지·문단·표·카드·목록)를 저장한다. 되돌리기·이력 복원은 관리자 화면에서 한다.
- **편집할 수 없는 것(🔒)**: 개인정보 문구·보유기간, 푸터 고지 문구, 메뉴 이름·구조, 신청 버튼 문구(신청 폼 정의), 레이아웃. 이런 요소에는 편집 표시가 붙지 않는다.
- **구현 위치**: 화면 조각의 데이터 위치는 렌더링이 붙인 `data-e`(저장 단위) · `data-f`(필드) · `data-block`(반복 블록) · `data-row`(반복 행)로 안다(`content.js`, `home.js`, `layout.js`). 편집 모드 코드는 `src/js/inline-edit.js`.
- **새 컴포넌트를 만들 때 규칙**: 콘텐츠를 그리는 새 컴포넌트는 위 표시를 붙여야 인라인 편집이 된다. 표시가 없는 요소는 편집되지 않는다(안전한 기본값).
- **한계**: 글자 서식, 이미지 업로드, 드래그로 위치·크기 조정은 지원하지 않는다. 모바일에서도 쓸 수 있지만 긴 문구는 데스크톱이 편하다. 두 사람이 동시에 같은 항목을 저장하면 나중 저장이 이긴다.

## 콘텐츠 웹 편집 (DB)
콘텐츠(현장명·전화·메인 문구·요약 수치·본문 문단·표·카드·목록·이미지 선택)를 **관리자 화면에서 웹으로 수정**할 수 있다. 기본 사이트와 템플릿 4종이 **같은 편집 화면**을 쓴다(2026-11-10, 사용자 요청).

- **적용 순서**: 기본(`config/base.ts`) → 유형 → 현장 파일(`config/site.ts`) → **DB에 저장된 웹 수정값(마지막, 우선)**. DB에 값이 없으면 파일 기본값 그대로 동작한다. API가 없거나 느려도(정적 호스팅) 3초 후 파일 기본값으로 동작한다.
- **저장 단위(scope)**: 유형 이름별로 따로 저장한다(기본 사이트는 빈 값). 데모처럼 DB 하나를 템플릿 4종이 함께 써도 서로의 수정이 섞이지 않는다. `SITE_TYPE`을 지정한 현장은 자기 유형만 쓸 수 있다.
- **어디서**: `/pages/admin.html` 로그인 → **콘텐츠 편집** 탭. 왼쪽에서 항목(기본 정보·메인 문구 / 본문 항목)을 고르고 오른쪽 폼에서 수정 → 저장. "수정됨" 표시, **초기값으로 되돌리기**(DB 수정값 삭제 → 파일 기본값), **이력 보기·복원**(수정 전 값 최근 20개), 꺼진 메뉴의 항목도 미리 입력 가능.
- **폼은 블록 종류로 자동 구성**: 이미지(목록 선택) · 소개 문단 · 표 · 카드 · 목록. 템플릿마다 항목 수가 달라도 같은 화면이다. 데이터는 하나, 그리는 컴포넌트만 템플릿마다 다르다.
- **웹에서 수정할 수 없는 것(사람이 확정, 감시 B5·B6)**: 개인정보 문구·보유기간, 푸터 고지 문구, 메뉴·레이아웃 구조, 신청 폼 항목. 서버가 저장을 거부한다. 개발자가 저장소의 설정 파일에서 바꾼다.
- **이미지 업로드는 없다**: 사진은 유형의 사진/이미지 세트(`src/assets/photos/<유형>/`)에서 모티프를 고르는 방식이다. 업로드는 별도 단계.
- **검증·보안**: 저장 전 서버가 형식·길이·개수를 검사한다(`config/content-schema.ts`, 화면과 서버가 공유). 모든 값은 이스케이프해서 그리므로 HTML이 실행되지 않는다. 쓰기는 관리자 토큰이 필요하다.
- **API**: `GET /api/content?scope=`(공개) · `PUT|DELETE /api/admin/content` · `GET /api/admin/content`(수정 목록) · `GET /api/admin/content/history`. 테이블: `site_content`, `site_content_history`(서버가 자동 생성).
- **개발자: 파일 ↔ DB 동기화** (`scripts/content-sync.ts`)
  ```bash
  npm run content -- export --scope full --out content.json    # DB → 파일 (백업·검토)
  npm run content -- import content.json --scope full          # 파일 → DB (검증 후 반영, 덮어쓴 값은 이력 보관)
  npm run content -- import content.json --scope full --replace --yes   # 파일에 없는 DB 항목까지 삭제(파괴적, --yes 필요)
  ```
  접속 대상은 `TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN`(없으면 로컬 `local.db`). **운영 DB에 쓰기 전에 반드시 export로 백업한다.** 파일(JSON)을 원본으로 git에서 검토한 뒤 반영하는 흐름을 권한다.
- **한계**: 두 사람이 같은 항목을 동시에 저장하면 나중 저장이 이긴다(이력으로 복원 가능). 개별 계정·수정자 기록은 아직 없다(비밀번호 1개). 현장 복제본의 DB는 새로 만들기 때문에 처음에는 비어 있다.

## 데모 미리보기 (템플릿 전체를 한 곳에서)
템플릿 4종은 **현장이 아니라 데모**다. 같은 사이트를 여러 구조·디자인으로 **화면 이동만으로** 보는 방식이다. 포트·서버·빌드를 유형마다 나누지 않는다.

- **개발 서버 하나(`npm run dev`, 5180)** 에서 모두 본다.
  | 주소 | 내용 |
  |---|---|
  | `/` | 기본(내부용 초안) |
  | `/guide/` | 가이드 매뉴얼 (기본에서만, 폴더 `guide/`) |
  | `/t/` | 템플릿 선택 페이지 |
  | `/t/minimal/`, `/t/full/`, `/t/mid-a/`, `/t/mid-b/` | 각 템플릿 (메뉴·링크가 `/t/<유형>/…` 안에서 이동) |
  - 기본 화면 푸터에 "템플릿 목록" 링크가 있고(기본 화면에서만 표시), 템플릿 상단 샘플 띠에는 "← 템플릿 목록" 링크가 있다.
- **유형은 주소를 보고 화면에서 정한다**(`/t/<유형>/`). 현장 빌드(`SITE_TYPE` 지정)는 기존처럼 그 유형 하나로 고정된다.
- **배포용 데모 빌드**: `npm run build:demo` (= `vite build --mode demo`). 빌드 **한 번**으로 `dist/t/<유형>/…` 전체와 선택 페이지(`/`, `/t/`)를 만든다. 가이드는 제외된다.
- **신청 기능은 현장 1개와 동일하게 동작한다**(결정: 2026-11-10, 사용자). 템플릿 구분 없이 `/api`와 DB 하나에 저장하고 관리자 화면(`/t/<유형>/pages/admin.html`)에서 본다.
  - 샘플 띠와 푸터에 "신청 기능은 실제로 동작하니 가상 정보로만 테스트하세요"를 표시한다. 필요하면 `sampleForm: true`로 저장을 끌 수 있다.
- **배포**: Vercel에 데모 전용 프로젝트를 만들고 같은 저장소를 Import한다. Build Command `npm run build:demo`, Output `dist`. 환경변수 `ADMIN_PASSWORD`, `TOKEN_SECRET`, `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`을 등록한다(`SITE_TYPE`은 등록하지 않는다). [미검증: 로컬 빌드 결과를 정적 서버로 확인함]
  - **데모 전용 Turso DB와 데모 전용 관리자 비밀번호를 쓰고, 실제 현장 값과 섞지 않는다.**

- 검색 노출은 막혀 있다(`noindex`, `robots.txt`). 외부 공유용으로 열지, 접근을 제한할지는 사람이 정한다.
