# 05. 전파 · 운영 · 종료

> 현재 단계 기준: 현장 최대 4개, 현장 1개 = 저장소 1개 = Vercel 프로젝트 1개 = Turso DB 1개. 자동 전파 도구는 만들지 않는다(범위 밖).
> 검증 표기: **[로컬 시험]** 로컬 임시 저장소로 확인함 / **[미검증]** 실제 GitHub·Vercel·Turso에서는 아직 시험하지 못함.

## 1. 템플릿 버전 관리
- 템플릿 저장소가 기준(upstream)이다. 공통(L1·L2·구조 코드) 수정은 **템플릿에서 먼저** 하고 현장으로 전파한다.
- 버전 형식: `template-vX.Y.Z` 태그. 현재 `0.1.0`(`package.json`의 `version`과 `CHANGELOG.md`를 함께 갱신).
  - **X**: 현장 복제본에 수작업이 필요한 변경(파일 구조, 설정 키 변경, 환경변수 추가)
  - **Y**: 기능 추가(새 L2 페이지, 관리자 기능)
  - **Z**: 버그 수정, 문구, 디자인 값
- 태그는 담당자가 직접 만들고 푸시한다: `git tag template-v0.1.0 && git push origin template-v0.1.0`
- 변경 내용은 `CHANGELOG.md`에 "현장에서 할 일(없음/설정 변경/수작업)"을 반드시 적는다.

## 2. 현장 × 버전 표
`docs/sites.md`에 현장마다 한 줄을 유지한다. (실제 현장명이 들어가므로 템플릿이 아니라 **운영 담당 저장소/문서**에서 관리해도 된다.)

| 현장 | 저장소 | Vercel 프로젝트 | 유형 | 템플릿 버전 | 마지막 전파일 | 상태 |
|---|---|---|---|---|---|---|
| (예) ○○ | org/site-a | site-a | standard | v0.1.0 | | 운영 중 |

## 3. 전파 절차 (공통 수정을 현장으로)
**원칙**: 현장 1곳(카나리)에서 먼저 확인한 뒤 나머지에 적용한다. 한 번에 4곳을 동시에 바꾸지 않는다.

1. **(최초 1회) 현장 저장소에 템플릿 연결**
   ```bash
   git remote add upstream <템플릿 저장소 주소>
   ```
2. **가져오기**
   ```bash
   git fetch upstream --tags
   git merge template-vX.Y.Z
   ```
3. **충돌 처리 규칙** [로컬 시험]
   | 충돌 | 처리 |
   |---|---|
   | 현장이 지운 유형·디자인 파일을 템플릿이 수정함 (`modify/delete`) | **계속 삭제**: `git rm <파일>` |
   | 수정 금지 파일(`api/`, `server/`, `src/js/`, `src/css/common.css`, `vite.config.js`, `vercel.json`, `config/base.ts` 등) | **템플릿 것을 채택** (현장은 이 파일을 고치지 않는 것이 원칙) |
   | `config/site.ts` | **현장 것을 유지** |
   | `package.json`, `package-lock.json` | 템플릿 변경을 받되, 현장에서 바꾼 항목이 있으면 확인 |
   | 현장이 교체/수정한 페이지·`config/modules.js`의 L3 추가 등 | 담당자가 판단. 판단이 어려우면 템플릿 쪽 `types/<이름>/REPLACED.md`와 비교 |
4. **점검 도구 실행**
   ```bash
   SITE_TYPE=<유형> npm run check:site -- --base template-vX.Y.Z
   ```
   수정 금지 파일이 템플릿과 다르면 FAIL로 알려 준다. [로컬 시험]
5. **빌드·로컬 확인**: `SITE_TYPE=<유형> npm run build` 통과, 신청 → 관리자 목록 확인
6. **푸시 → Vercel 자동 배포 → 배포 주소에서 신청 → 관리자 확인** (테스트 데이터는 삭제) [미검증]
7. `docs/sites.md`의 버전·전파일을 갱신하고 `CHANGELOG.md`의 "현장에서 할 일"을 처리한다.

**롤백**: 병합 커밋을 `git revert -m 1 <병합 커밋>`로 되돌려 푸시하거나, Vercel의 이전 배포를 다시 배포(Promote)한다. [미검증]

> 공통 수정 1건을 실제 현장 2곳에 전파해 보는 검증은 **실제 저장소가 있어야 하므로 아직 못 했다.** 위 3·4번은 임시 저장소(템플릿 1 + 현장 1)에서 충돌 처리와 점검 도구까지 확인했다.

## 4. 오픈 전 점검
### 도구로 확인 (`npm run check:site`)
- 샘플·가상 문구가 남지 않았는가(현장명, 전화, 본문, 고지, 메인 문구, 수집 목적)
- `sample`, `sampleForm`이 꺼져 있는가 (신청이 저장되는가)
- 개인정보 보유기간이 확정됐는가
- 가이드 화면·`docs/`가 현장 저장소에 남지 않았는가
- `.gitignore`에 `node_modules`, `dist`, `.env.local`, `local.db`가 있는가
- 수정 금지 파일이 템플릿과 같은가(`--base`)

### 사람이 확인 (감시 B3~B9)
- [ ] `ADMIN_PASSWORD`, `TOKEN_SECRET`이 **이 현장 전용 값**이고 임시값(`admin1234` 등)이 아닌가
- [ ] 동의문의 수집 항목과 폼 항목이 일치하는가, 보유기간·수집 목적을 확정했는가
- [ ] 고지 문구(이미지 연출, 변경 가능성, 광고 표기)를 확정·검토했는가
- [ ] 대표전화·주소·운영시간 오탈자를 확인했는가
- [ ] 관리자·내부용·가이드 화면이 공개 배포에 없고, 검색 노출 정책(`noindex`)이 의도대로인가
- [ ] **공개 주소**에서 신청 → 관리자 목록 확인 후 테스트 데이터를 삭제했는가
- [ ] 환경변수를 바꿨다면 **재배포**했는가
- [ ] Vercel 플랜이 상업적 사용에 맞는가 (Hobby는 약관상 제한)

## 5. 운영 (4개 현장)
- **신청 확인**: 현장 관리자 화면(`/pages/admin.html`). 조회·상태 변경·CSV 다운로드 가능. 신규 신청 알림은 없다.
- **담당 정하기**(사람이 정함): 현장별 관리자 비밀번호 보관자, 신청 확인·전달 담당, 대행사 전달 방식(화면 확인 / CSV / 알림)
- **콘텐츠(웹 수정값) 백업**: 관리자에서 문구를 고치는 현장은 정기적으로(그리고 전파·큰 수정 전에) `npm run content -- export --scope <유형> --out content.json`으로 백업한다. 웹 수정값은 코드 전파와 무관하게 DB에 남는다.
- **비밀값**: 현장마다 다르게, 담당자가 별도로 보관. 퇴사·교체 시 `ADMIN_PASSWORD`, `TOKEN_SECRET`을 바꾸고 재배포(기존 로그인 토큰은 무효가 된다).
- **정기 점검(제안)**: 주 1회 각 현장에서 신청 테스트 1건 → 확인 → 삭제. 전파 직후에는 카나리 현장에서 먼저.

## 6. 종료 · 파기
현장 분양이 끝났을 때의 절차. **삭제는 되돌릴 수 없으므로 사람이 결정·실행한다**(AI가 대신 삭제하지 않는다, 감시 B8).

1. **신청 마감**: `config/site.ts`에 `formClosed: true` (필요하면 `formClosedMessage`) → 푸시·배포. 화면은 안내문만 보이고 서버도 신청을 거부한다(403). [로컬 시험]
2. **보존기간 확인**: 동의문에 적은 보유기간까지는 데이터를 유지한다. 기간·담당자를 `docs/sites.md`에 기록해 두고 도래일을 챙긴다.
3. **데이터 인계·백업 여부 결정**: 필요하면 관리자 화면에서 CSV를 내려받아 대행사/담당자에게 안전한 방식으로 전달한다. 개인정보이므로 메신저·메일 첨부로 장기 보관하지 않는다.
4. **파기(보유기간 후)**: Turso에서 해당 현장 데이터베이스를 삭제한다. (신청 데이터와 웹 수정 콘텐츠 테이블이 함께 사라진다. 콘텐츠를 남기려면 먼저 export) 삭제 일시·담당자를 기록한다. [미검증]
5. **사이트 정리**: Vercel 프로젝트를 중지/삭제하고, 저장소는 보관(archive) 또는 삭제를 정한다. 도메인은 별도 처리.
6. `docs/sites.md`의 상태를 "종료", 파기일을 기록한다.

## 7. 아직 사람이 정해야 할 것
- 대행사에 신청 데이터를 전달하는 방식(화면/CSV/알림)과 알림 도입 여부
- 개인정보 보유기간, 파기 책임자
- 접수 종료 후 CSV 백업을 남길지 여부
- 실제 현장 2곳에서의 전파 시험, 종료·파기 1회 수행 (S7 완료 기준)
