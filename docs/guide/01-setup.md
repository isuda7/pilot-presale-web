# 1. 세팅 · 가입 · 판단 노하우 · 진행 과정

> 이 장은 이 프로젝트를 처음 만든 과정에서 실제로 헷갈렸던 지점을 기준으로 쓴 것이다.
> 비밀번호·토큰·DB 접속값은 이 문서에 적지 않는다. 환경변수로만 다룬다.

## 1. 구성 한눈에 보기
| 역할 | 서비스 | 설명 |
|---|---|---|
| 코드 저장 | GitHub | 현장 1개 = 저장소 1개 |
| 실행·배포 | Vercel | 프론트 빌드 + 백엔드(Hono) 실행. 저장소에 푸시하면 자동 빌드·배포 |
| 데이터 | Turso | 신청 데이터를 저장하는 DB. 현장 1개 = DB 1개 |

- 백엔드(처리)는 Vercel에서 돌고, 데이터는 Turso에 저장된다. 처리와 데이터는 별개다.
- 로컬에서는 내 컴퓨터에서 `npm run dev`가 웹(5180)과 API(8790)를 띄우고, DB는 `local.db` 파일을 쓴다. Turso는 배포용이다.

## 2. 로컬 환경 만들기
```bash
npm install
npm run dev
```
- 로컬 환경변수는 `.env.local`(저장소에 올리지 않음)에 `ADMIN_PASSWORD`, `TOKEN_SECRET`을 적는다. 값은 임시로 정하되 운영 값과 다르게 한다.
- 템플릿 확인: `npm run dev` 후 `http://localhost:5180/t/`에서 선택 (유형별 서버·포트가 필요 없다). 현장처럼 유형 하나로 고정해 보려면 `SITE_TYPE=minimal npm run dev`.
- 포트가 이미 쓰이고 있으면 다른 프로젝트의 서버일 수 있다. 함부로 끄지 말고 다른 포트로 띄운다.

## 3. 가입·연결 절차 (현장 1개 기준)
1. **GitHub**: 템플릿 저장소에서 새 저장소를 만든다.
2. **Turso**: 새 데이터베이스를 만든다. 무료 플랜 이름은 화면에 따라 "Free" 또는 "Starter"로 다르게 보인다.
3. **Vercel**: GitHub 저장소를 Import한다. Framework는 Vite 자동 인식, 루트는 저장소 루트.
4. **Turso 연결**: Vercel의 Storage/Integrations에서 Turso를 추가하고 새 프로젝트에 연결하면 `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`이 자동 등록된다. (Custom Prefix를 쓰면 변수 이름이 바뀌니 쓰지 않는다.)
5. **직접 등록할 환경변수**: `ADMIN_PASSWORD`, `TOKEN_SECRET`, 유형을 쓰는 현장은 `SITE_TYPE`.
   - `TOKEN_SECRET`은 길고 예측할 수 없는 문자열(32자 이상). 관리자 로그인 토큰의 서명에 쓰는 값이며 사람이 외울 필요가 없다. 현장마다 다른 값을 쓴다.
   - `ADMIN_PASSWORD`는 사람이 로그인할 때 입력하는 값이다. 담당자가 별도로 보관한다.
6. **재배포**: 환경변수는 저장해도 **새 배포부터** 적용된다. 값을 바꿨으면 반드시 다시 배포한다.
7. 배포 주소에서 신청 → 관리자 로그인 → 목록 확인 → 테스트 데이터 삭제까지 직접 해본다.

## 4. 헷갈리기 쉬운 판단 노하우 (실제 사례)
| 상황 | 원인 | 판단·해결 |
|---|---|---|
| Vercel에서 GitHub 가져오기를 눌렀더니 Pro 체험 화면이 나옴 | GitHub **조직(org)** 저장소를 연결하면 팀 플랜 화면이 나온다 | 개인 계정 저장소로 연결하면 무료(Hobby). 단, Hobby는 약관상 **상업적 사용 제한**이 있어 실제 분양 운영 전에 플랜을 확인한다 |
| 배포가 실패하거나 `/api`가 `FUNCTION_INVOCATION_FAILED` | 서버 코드의 상대 import에 `.js` 확장자가 없었다 (ESM 서버리스는 확장자 필수) | 서버·설정 TS의 상대 import에는 `.js`를 붙인다. 로컬에서 되는데 배포에서만 깨질 수 있다 |
| 관리자 비밀번호가 배포 주소에서 안 맞음 | ① 환경변수를 바꾸고 재배포하지 않았다 ② **예전 배포 URL**을 열었다(고정된 옛 배포, 로그인 보호가 걸려 있을 수 있음) ③ 자릿수를 잘못 입력했다 | 프로젝트 도메인에서 확인한다. 옛 배포 주소로 판단하지 않는다. 로컬과 서버의 비밀번호는 서로 별개다 |
| 로컬에서 로그인이 안 됨 | 새 폴더에 `.env.local`이 없었다 | `.env.local`을 만든다 (저장소에는 올리지 않는다) |
| 저장소가 매우 커짐, 파일 4천 개 | `node_modules`, `dist`가 커밋됐고 `.gitignore`가 없었다 | `.gitignore` 확인, 이미 올라갔다면 추적 해제 후 커밋 |
| 환경변수 이름이 Turso 연동과 다름 | 연동 시 Custom Prefix를 줬다 | 코드가 읽는 이름은 `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`이다. 접두사 없이 연동한다 |
| 푸시가 안 됨 | 자동화 도구에는 GitHub 로그인 정보가 없다 | 푸시는 담당자가 직접 한다 |

## 5. 진행 과정 (프롬프트로 진행한 순서)
이 프로젝트는 AI와 대화하며 다음 순서로 진행했다. 새 현장을 만들 때도 같은 순서를 따른다.

| 단계 | 한 일 | 이때 AI에게 준 지시의 형태 |
|---|---|---|
| 환경 | 기존 프로젝트를 "참고 예시"로 주고 같은 성격의 환경(백엔드·프론트·신청·관리자) 요청 | 그대로 복사하지 않고 참고만 한다고 명시 |
| 배포 | "Vercel로 통일", "Turso 가입 전" 같은 현재 상태를 있는 그대로 전달 | 모르는 개념은 그대로 질문한다 (처리/데이터 분리 등) |
| 벤치마킹 | "선착순이 아니라 평균적인 10개" | 선정 기준을 명시한다 |
| 설계 | "공통을 어떻게 가져가고, 데이터를 어떻게 바꾸고, 사이트를 어떻게 생성할지" 3가지 관건 제시 | 현재 단계의 범위를 못 박는다 (복제+수정, 4개 현장, 도메인 제외) |
| 구조 | L1~L4, 내부용/외부용/매뉴얼, 덮어쓰기 구조를 사용자가 직접 제안 | AI의 제안을 받아 사용자가 구조를 확정한다 |
| 정리 | 전체 기획·단계별 범위·원본/감시 프롬프트 문서화 (`docs/01~03`) | "AI가 알아서 하는 것은 빼고, 놓치기 쉬운 것과 사람의 판단 규칙만 감시 프롬프트로" |
| 구현 | S1 → S2 → S3 → S4 순서로 진행 | 단계 순서를 지키고, 단계마다 확인하지 못한 것을 "미확인"으로 보고받는다 |

### 프롬프트 운용 원칙
- 원본 프롬프트(기획 전체)와 감시 프롬프트(규칙)는 `CLAUDE.md`에 등록되어 있어 새 작업 세션이 시작될 때 자동으로 읽힌다. 원문은 `docs/03-prompts.md`가 기준이다.
- 막히면 증상(화면 문구, 에러 메시지)을 그대로 붙여 질문한다. 추측한 원인을 단정해서 말하지 않는다.
- AI가 "확인하지 못했다"고 한 항목은 사람이 직접 확인해야 완료다. 특히 배포 환경의 동작.
- (미정) 이 장의 "진행 과정"을 대화 기록 요약으로 유지할지, 재사용할 프롬프트 예시 모음으로 바꿀지는 사람이 정한다.

## 6. 현장 복제 시 정리할 것
> 2026-11-10 로컬 복제 시험(빈 폴더에 복사 → 정리 → 설치 → 빌드 → 신청 API 시험)으로 확인한 내용이다. GitHub 새 저장소·Turso DB·Vercel 프로젝트를 실제로 만드는 부분은 **아직 시험하지 못했다**(3절 절차 기준, 미검증).

1. **가이드 화면·문서 제거**: `guide/` 폴더와 `docs/`를 삭제한다. (`SITE_TYPE`을 지정한 빌드에서는 가이드 화면이 자동으로 빠지지만 파일이 남지 않게 한다.)
2. **쓰지 않는 유형·이미지 정리**: `types/*`, `src/assets/art/<유형>/`, `src/assets/photos/<유형>/`(+ `CREDITS.md`)에서 쓰지 않는 것을 지우고 `types/index.ts`의 등록 줄도 지운다. `scripts/gen-art.mjs`는 필요 없으면 지워도 된다.
   - ⚠ 유형이 다른 유형을 가져다 쓰는 경우(`import`)가 있으면 그 유형과 `types/shared/`는 남긴다. 지우고 빌드가 깨지면 이 경우다.
3. **현장 데이터 입력**: `config/site.ts`에 현장과 다른 값만 적는다.
   - ⚠ **샘플 유형(`minimal`, `full`, `mid-a`, `mid-b`)을 실제 현장에 쓸 때는 반드시** `sample: false`를 적는다(상단 "샘플" 띠 제거). 샘플 유형의 기본값은 `sampleForm: false`라 신청은 저장되지만, `sampleForm: true`가 남아 있으면 **신청이 저장되지 않으니** 함께 확인한다. (서버도 같은 설정을 읽어 판단한다.) 신청 문구(`privacy`)와 푸터 고지에 "샘플·시연" 문구가 남았는지도 확인한다(`npm run check:site`가 잡아 준다).
   - 그 밖에 `name`, `phone`, `address`, `notices`, `privacy`(보유기간·목적), `content`(본문), `showAdminLink`, `noindex`를 현장 기준으로 정한다. 기획 자료에 없는 값은 적지 않는다.
4. **가상 데이터 제거**: 샘플 유형의 본문은 `types/shared/virtual.ts`의 가상 프로젝트 데이터(이름·카피·수치·메인 요약 `hero.facts`·주소 포함)다. `config/site.ts`의 `content`로 현장 본문을 덮어쓰고, 덮어쓰지 않은 모듈에 가상 문구가 남지 않았는지 화면에서 하나씩 확인한다. (모듈별로 `content`를 모두 채우거나 해당 모듈을 끈다.)
5. **`CLAUDE.md`**: 감시 규칙을 현장 기준으로 조정한다(수정 허용 범위 A6).
6. **콘텐츠 DB**: 새 Turso DB는 비어 있고 첫 요청에 테이블이 자동 생성된다. 웹 수정값은 없으므로 처음에는 파일 기본값이 나온다. 관리자 → 콘텐츠 편집에서 현장 문구를 입력하거나 `npm run content -- import`로 파일을 반영한다(`docs/04-site-edit-guide.md`).
7. **비밀값**: `ADMIN_PASSWORD`, `TOKEN_SECRET`을 현장 전용 값으로 새로 정한다. 내부용 초안의 임시값을 가져오지 않는다.
8. **빌드 확인**: `SITE_TYPE=<유형> npm run build`가 통과하고, `dist/`에 `guide/` 폴더가 없는지 확인한다.
9. 내부용 초안(유형 없는 빌드)을 배포하면 가이드 화면이 함께 열린다. 공개 범위(접근 제한)는 사람이 정한다.

### 복제 시험에서 막혔던 곳 (매뉴얼에 반영 완료)
| 막힌 곳 | 원인 | 반영 |
|---|---|---|
| 유형을 지우자 빌드 실패 | 유형이 다른 유형을 가져다 씀 | 위 2번 경고 |
| 현장에서 `sampleForm:false`로 바꿨는데 신청이 저장되지 않을 수 있었음 | 서버가 현장 설정을 읽지 않고 유형만 보고 판단했음 | 코드 수정(서버가 기본 → 유형 → 현장 병합 결과를 사용) + 위 3번 경고 |
| 가이드 관련 CSS가 현장 빌드에 남음 | 가이드 스타일이 공통 CSS에 있었음 | `guide/guide.css`로 분리해 가이드 화면에서만 로드 |
